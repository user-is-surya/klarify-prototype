# Klarify Review-2 Prototype: Design

Date: 2026-11-20. Team REVENANTS.exe (DT project). Status: awaiting approval.

## Intent and why
Review 2 requires a *hardware prototype*. Time is short and several reviews remain, so scope is
deliberately cut. The prototype must show the core Klarify promise end to end: a sound happens ->
the ESP32 classifies it on the device -> a hearing-impaired person gets a clear visual alert on a
separate portal. Input sound is **synthetic** (generated by us), and this is stated openly in the
demo. Real microphone, smartwatch and ML on real recordings are later reviews.

## Goals
- G1. A classifier running **on the ESP32** that labels a 1-second audio window as one of:
  cooker whistle, doorbell, baby cry, smoke alarm, microwave beep, background noise.
- G2. A laptop **sound generator** that creates those synthetic sounds (with random variation and a
  controllable noise level) and streams them to the ESP32 as raw audio over USB serial, in real time.
- G3. A **separate portal** (web page hosted by the ESP32, opened on a phone joined to the ESP32's
  own Wi-Fi; needs no internet) showing: full-screen colour by alert level, big icon + sound name,
  time, history log, per-sound mute, and a "simulated input" badge.
- G4. Alert levels from slide 14: Urgent/red (smoke alarm, cooker whistle), Important/amber (baby
  cry), Info/blue (doorbell, microwave beep). Background noise raises no alert.
- G5. The "two detections in a row" rule from slide 17 to suppress false alarms.
- G6. Onboard LED mirrors the level (urgent: fast continuous blink, important: two blinks, info: one).

## Non-goals
Real microphone (INMP441), smartwatch / BLE / watch app, water probe, tank-overflow sound,
user-taught sounds, Telegram/ntfy/cloud, real-world accuracy claims, battery/enclosure.

## Anti-goals (a failure even if it technically works)
- Presenting accuracy measured on our own synthetic sounds as real-world performance.
- A demo that depends on venue internet or on the audience's Wi-Fi.
- Classification secretly done on the laptop, so the ESP32 is just a display.

## Constraints
- Hardware: ESP32-WROOM-32 38-pin NodeMCU, USB cable, breadboard, jumper wires. Nothing else.
  The board is physically with a friend (Windows laptop, CP210x driver installed); we cannot test on it from here.
- ESP32 has ~320 KB RAM (no PSRAM): audio window must be small.
- Laptop: Windows 11, Python 3.13, Node present. Arduino IDE / PlatformIO are **not** installed;
  no COM port was visible when checked (board unplugged or USB-serial driver missing).
- The board stays the only "device"; the phone is a browser only (no app install).

## Approaches considered
1. Buttons trigger canned alerts via ntfy. Quickest, but needs internet and the "detection" is fake. Rejected.
2. **(Chosen)** Synthetic audio streamed to the ESP32, real on-device feature extraction + tiny
   model, ESP32-hosted portal. Real code path; only the audio *source* is simulated, so a real I2S mic
   later replaces one function.
3. Everything on the laptop, ESP32 as display. Rejected: not a hardware prototype.
Portal placement: phone on ESP32 hotspot (chosen) vs laptop browser on projector (rejected as default;
the same page also opens from a laptop joined to the hotspot).

## Architecture
```
Laptop (Python)                 ESP32 (PlatformIO / Arduino)                   Phone browser
tools/synth.py  --PCM 8 kHz-->  serial reader -> 1 s window -> features  -->   portal (HTML from ESP32)
tools/feed.py   (USB serial)    -> decision tree -> 2-in-a-row -> state        polls /api/state
 (CLI: keys pick sound,         LED pattern + SoftAP "Klarify-Demo"            (colour, icon, log, mute)
  noise level, auto-playlist)
```

### Audio format (my call)
8 kHz, 16-bit mono, 1-second windows (8000 samples = 16 KB), hop 0.5 s. Framed over serial at
921600 baud with a sync header + sequence number so the ESP32 can resync. Generator paces in real time.

### Features and model (my call)
Short-time frames (512-point FFT, own small radix-2 FFT, no library): dominant frequency, spectral
centroid, spectral flatness, bandwidth, energy-envelope pulse rate / duty cycle, harmonic ratio.
Model: a small decision tree trained in Python (scikit-learn) on thousands of generated clips with
random pitch, level and noise, **exported as a C header** (`model.h`). Feature code exists in Python
(training) and C++ (firmware); parity is verified by having the firmware echo its features for a known
clip and comparing to Python within tolerance.

### Synthetic sounds (my call, loosely modelled on real signatures)
Cooker whistle: ~2.5-3.5 kHz tone, rising/falling pulses. Doorbell: two-tone ding-dong. Baby cry:
harmonic ~400-600 Hz with vibrato and bursts. Smoke alarm: ~3 kHz, 3 beeps then pause. Microwave
beep: short ~2 kHz beeps. Background: broadband noise with occasional clatter-like clicks.

### Portal / API (my call)
Single HTML page embedded in firmware, served by the ESP32 in SoftAP mode (SSID `Klarify-Demo`).
Page polls `GET /api/state` every ~300 ms (no WebSocket library). `POST /api/mute?sound=..` toggles mute.
Phone vibration uses the browser Vibration API where supported (Android Chrome, after one tap);
iPhone gets colour + on-screen alert only. Tested on the real phone before the review.

## Project layout
`firmware/` (PlatformIO project), `tools/` (synth, train, feed), `docs/`.

## Delivery (board and demo run on a friend's Windows laptop)
The ESP32 is **not** with us; it is connected to a friend's Windows laptop, which already has the CP210x
universal driver. We build and test here (firmware is compiled only; Python side fully tested), then ship a
zip `klarify-demo/` that needs no installs on their machine:
- `flash.bat` + bundled `esptool.exe` + merged `firmware.bin`: double-click flashes the ESP32 (auto-detects the COM port).
- `klarify-feeder.exe`: PyInstaller build of the generator/feeder CLI (no Python needed there).
- `README.txt` (one page): flash, run feeder, join `Klarify-Demo` Wi-Fi on the phone, open the portal; troubleshooting.
- Self-test: the feeder pings the ESP32, firmware replies with its version, portal shows "connected".
- First hardware run happens on their setup, so a short trial session before the review is a must.
- The Python source stays in `tools/` as a fallback if the exe misbehaves.

## Testing and demo evidence
- Python: classifier accuracy on a held-out *synthetic* set, labelled as such, per-class confusion matrix.
- Firmware: parity check (features) and an end-to-end run for each of the 5 sounds + background.
- Measured end-to-end delay (sound start to portal change), reported honestly.

## Left to the builder
Exact thresholds, tree depth, icon art, page styling, CLI key bindings, auto-playlist order.

## Risks
- Untested on real hardware until the friend's setup -> self-test, README troubleshooting, trial run beforehand.
- Antivirus may flag the PyInstaller exe -> ship the Python source as a fallback.
- Serial streaming glitches -> sync header + resync; fallback is a smaller window or lower baud rate.
- Synthetic-to-synthetic accuracy looks too perfect -> add noise/variation, and say what it is.
